# Security

This project ships a **zero-extra-dependency** security middleware
(`webapp/security.py`) plus hardening in data handling. Below is the threat model,
what is implemented, and what is intentionally out of scope.

## Threat model

| Asset | Risk | Mitigation |
|-------|------|------------|
| Dashboard API | Unauthorized access / data exfil | `DASHBOARD_TOKEN` auth + CSRF headers |
| Mutating endpoints | Cross-site state changes | CSRF defense |
| Scraper status / DB | Resource abuse | Rate limit, lock guard |
| Uploads | Malicious files / path traversal | Extension + size whitelist, sanitized names |
| Local-only installs | Over-broad exposure | Default-deny auth when token set |

## Authentication (`require_auth`)

- When `DASHBOARD_TOKEN` is **empty** (default), the app is treated as local-only:
  auth is skipped (`FREE_PATHS = {"/", "/dashboard.html"}` still served).
- When set, every API request must send the token. It is accepted via:
  - `X-Auth-Token` header (recommended)
  - `X-CSRF-Token` header
  - `?token=` query param (kept for convenience)
- Comparison uses `hmac.compare_digest` — **constant time**, so token checks do not
  leak timing information.
- The dashboard page itself is exempt; the UI stores the token in `localStorage` and
  attaches it to every `fetch` call.

## CSRF defense (`require_csrf`)

State-changing requests (`POST/PUT/PATCH/DELETE`) must carry a custom header. Custom
headers cannot be added by a cross-origin `<form>` or `<img>` (the browser would
trigger a preflight), so this neutralizes CSRF **without cookies/sessions**.

- Skipped when `DASHBOARD_TOKEN` is empty (local-only mode).
- Else: valid header → allowed; missing → `403 {"error": "CSRF token required."}`.

## Rate limiting (`apply_rate_limit`)

In-memory **sliding window**: `RATE_LIMIT_MAX = 60` requests per
`client:{method}:{path}` per `RATE_LIMIT_WINDOW = 60` seconds, keyed on the private
address family of `request.remote_addr`. When exceeded → `429`.

- Skipped when `current_app.config["TESTING"]` is true, so tests and CI can hammer
  endpoints.
- State is a module-level `defaultdict(deque)`; acceptable for a single-process
  personal dashboard, **not** for multi-process gunicorn behind a load balancer
  (see "Out of scope").

## Response hardening (`apply_security_headers`)

Applied to every response via `after_request`:

- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY` — no framing
- `Referrer-Policy: no-referrer`
- `X-XSS-Protection: 1; mode=block` (legacy; CSP does the real work)
- `Content-Security-Policy`: `default-src 'self'`; images may come from `https:`/`data:`
  (job logos, company avatars); `frame-ancestors 'none'`; `base-uri 'self'`;
  `form-action 'self'`. `style-src`/`script-src` allow `'unsafe-inline'` because the
  dashboard is a single static HTML file with inline styles/scripts.
- `Strict-Transport-Security` (only when the request was HTTPS)
- `Cache-Control: no-store`

## Input hardening

- **Uploads** (`webapp/routes/resume.py`):
  - Extension whitelist `{.pdf .doc .docx .md .txt}`
  - `MAX_FILE_SIZE = 16MB`, also enforced server-side (`MAX_CONTENT_LENGTH`)
  - Filename checked for `/` and `\` → rejects path traversal; stored as a fixed
    `resume<ext>` name so the client can never control the destination path
  - DOCX parsed as a **zip entry** (`word/document.xml`) with `xml.etree` — the XML is
    generated by office software and bounded by the zip/16MB limits, so it is treated
    as a closed input format
  - Parse failures are caught and degrade to empty content (never crash the pipeline)
- **Job ids / statuses** (`models.py`): `validate_job_id` rejects control characters;
  status transitions validated against `VALID_STATUSES`.
- **Settings**: `POST /api/settings` deep-*merges* (never wipes unrelated sections).

## Known out-of-scope items

Documented so future maintainers make an informed choice:

- **HTTPS/TLS, secrets storage, Auth strategies beyond a token** are deployment-level
  (Render, reverse proxy, Docker) — this layer assumes presentation is secure.
- The in-memory **rate limiter is per-process**: with gunicorn workers >1 each worker
  keeps its own window. Acceptable for the intended single-user dashboard; swap for a
  shared store (Redis) if exposed to the internet at multi-worker scale.
- Legacy scrapers (`agy_filter`, `browser_agent`, `job_freshness`, `job_alerts`)
  still show low-severity bandit findings (mostly `B404` subprocess import and
  `B603` command strings) that are **intentional** — they exec locally-built commands
  with parameters validated upstream. These are excluded from the CI security gate.
- `SECRET_KEY` and `DASHBOARD_TOKEN` ship safe defaults but **must be overridden** in
  production via `.env` (see deployment notes).

## Verifying

```bash
bandit -c pyproject.toml webapp app.py models.py repositories.py schema_migrations.py \
       rule_filter.py score_adjuster.py resume_parser.py resume_scanner.py config.py database.py
```

Expect **0 findings** on the webapp + domain core. Tests additionally assert the
401/403/429 paths, CSP header presence, token comparison, and upload rejection
behaviors.
